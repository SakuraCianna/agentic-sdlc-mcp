# v1.11.0

Status: release candidate. A version in source is not proof of npm or MCP Registry publication.

This candidate combines the previously implemented v1.10 contract/evaluation work with practical read-only PR delivery. The last public version verified during this work was v1.9.0; no historical v1.10 release is fabricated.

## User-facing delivery

- A second binary, `agentic-sdlc`, provides `doctor`, `assess-pr`, `evidence`, `diff` and `trace`. MCP startup remains `agentic-sdlc-mcp`.
- PR assessment reuses the production gate and review, binds immutable head/base SHAs and policy, and reports concrete blockers/actions. Advisory is default; enforcement is explicit.
- The opt-in reusable workflow uses a published exact reviewer version, read-only GitHub access and no PR checkout/execution. Verified current-check dependency is reported separately without rewriting GitHub's actual gate.
- Evidence continuity reports additions, removals, changes and target/policy/version/expiry invalidation. Prior verification is never inherited.
- Acceptance conditions have stable source/content identities. Positive acceptance verification requires matching complete 40- or 64-character hexadecimal SHAs and a valid PR/Issue number where applicable. A checked box, ordinary CI pass or caller mapping cannot prove business satisfaction; the CLI has no trusted producer configured by default.
- Diagnostics and CLI use environment credentials only. MCP additionally supports `SDLC_CONFIG_MODE=envonly`; compatibility home configuration remains the default when this mode is absent.
- `SDLC_READ_ONLY=true` disables live Issue creation while preserving preview.
- The client recipes, portable review Skill and privacy-preserving pilot provide concrete adoption paths with explicit verification levels.

## Correctness and recovery

Code Scanning security severity takes precedence over generic SARIF severity. Invalid unknown severity marks incomplete evidence. PR gate and review share work-type classification for repository risk/reviewer rules.

Issue creation propagates cancellation, stops new items after unknown outcomes and preserves confirmed/unknown results during cancelled recovery. Optional `previewDigest` and `idempotencyKey` options use request-level `params._meta["io.github.SakuraCianna/agentic-sdlc-mcp/issue-recovery"]`, not tool arguments. Preview digests bind the repository and payload; keys support bounded marker/payload recovery. Clients unable to attach metadata retain default preview/basic reporting and must not assume automatic idempotent retries. These options are not authorization or cross-process exactly-once guarantees.

PR reads detect target drift throughout collection, including a temporary different head. Request budgets in decision packets reflect the actual configured request/deadline limits and participate in the digest. CLI SDK logging is disabled; error output uses safe bounded diagnostics.

## Engineering and distribution

The 13 tools and five static resources remain. New Issue output fields are additive; the existing tool argument shape is preserved, and recovery options use a separate request metadata namespace. Node 22+ remains the runtime floor; CI includes a Windows CLI/stdio smoke job.

`release:prepare` first builds the reviewed checkout, then packs with npm lifecycle scripts disabled and isolated npm user/global configuration. It produces an inspected tarball, a lockfile-derived CycloneDX SBOM with development dependencies omitted, and a SHA-256 source/package manifest; it does not publish, sign, or overwrite existing output directories. The manifest records actual source digests and dirty-tree state, so HEAD alone does not identify a dirty candidate. This is local preparation, not deployment inventory or a reproducible-build attestation; signed artifact attestations and automatic SBOM publication are not claimed.

## Upgrade and rollback

Keep least-privilege GitHub credentials. After installing an available exact release, restart the MCP client connection and inspect server discovery; already running processes do not hot-reload a new package.

For regression rollback, pin a previously verified published version and restart. Do not reuse a published version or bypass required checks. Preserve raw unknown-write outcomes and verify Issue URLs before retrying with a different key.
